# SceneVoice 影院版：电影口述影像桌面工具（计划）

日期：2026-11-15　基线：`main` 2215d98（扩展 1.1.0 + 网页播放器）

依据：21 份调研（其中 15 份各做过一次对抗式核查——每份抽查约 6 条关键结论，只直读一手页面；搜索额度用尽，没做开放检索；另 6 份追加调研未经核查）、5 份代码梳理、4 版独立设计、3 位评委；本计划成稿后又经 6 路审查，39 条问题逐条经独立代理反驳后全部成立，已改入本文。文中“（待测）”的数字是假设，由第 0 阶段的实验确认或推翻；竞品与专利的开放检索已于 2026-11-15 补做（`docs/film/competitors-and-patents.zh-CN.md`），第三节第 1、11 条和第十一节据此改写；专利库没有查全，“没有相关专利”仍不能下结论。

## 一、背景：为什么做、要做成什么

需求调研里视障观众说得很明确：看电影时不想一遍遍听“一个穿红裙子的女人走来走去”，而是在第一次认识主角和她的着装之后，听到一个确定的人——“马修穿着红裙子来回踱步”。他们还需要不同的声音可选；志愿者需要一份能直接照着配音的口播稿。

现有 SceneVoice 做不到，原因在代码里很具体：

- **人物只存在于提示词里。** `characters[]` 只有 `{label, description}`，按标签字面去重、只增不改，只把前 20 个回传给模型（`src/shared/gemini.js:11-18`、`src/shared/script.js:223-259`）。后来学到名字，只会多出一个互不相连的新条目。一条口述没有 id、没有结束时间、不记录“这句说的是谁”。
- **没有电影入口。** 只认 YouTube / Bilibili 的视频 id，没有本地文件路径；会员流媒体有 DRM，画面读不到。
- **声音只有两种**（用户的读屏、浏览器内置语音）；口播稿只能下载 `.txt`（`src/transcript/transcript.js`），没有导出、录音、混音代码。

**目标成果**：一个独立桌面软件（暂名 **SceneVoice 影院版**），把用户手里的本地影片变成带“角色锁定”的口述影像——视障者在软件里边放边听，志愿者在同一软件里确认角色表、改稿、逐句配音、导出口播稿，成品以“口述包”送到其他视障者手里。质量对标能融资的公司：每个关键主张都有可复现的测量数据、合规规则写进代码和测试、签名安装包与自动更新。

## 二、你已经确认的决定

| 问题 | 决定 |
| --- | --- |
| 影片来源 | 本地视频文件（用户已合法持有，无 DRM） |
| 谁来制作 | 两条线都做：视障者自助生成 + 志愿者/机构制作台 |

## 三、调研结论（决定方案的事实）

1. **角色身份必须放在大模型之外的确定性层。** 最好的系统都是：镜头切分 → 人脸轨迹 → 片内聚类 → 角色库 → 在画面的人脸上画彩色编号框，并在文字里给“编号 = 谁”的对照表。名字写在文字里比画进图里准；10 分钟分段 + 随段携带的角色库，比整部电影一次塞给模型准。公开的带编号框身份问答成绩（英文片、旧型号，不能直接套到现行型号或华语片）：最好的 97，千问 86，Gemini 83，豆包无数据——所以“模型会不会照我们给的身份写”是第一个要测的事。让模型只写人物编号、事后映射成名字是已有做法（MICap、BAC）；不靠演员表、从对白取名的角色库也已有（MM-Narrator、牛津 StreamCast，后者自测点名准确率 72.8%，这正是需要人确认的理由）。开放检索未见的是：用代码强制执行点名规则的闸门，和按场景的着装记忆。
2. **能合法商用的人脸模型很少，且没有电影上的公开成绩。** 可用：YuNet 检测（MIT）、SFace 特征（Apache-2.0）、AuraFace-v1（Apache-2.0，但精度有争议、训练数据来源未答复；同仓库里的检测与关键点文件是 InsightFace 的非商业文件，不能用）。InsightFace 全家、EdgeFace、YOLO-face 的权重是“仅限非商业”或 GPL。已发表的电影数据全用 InsightFace 测得，东亚面孔上差距明显。**必须自己实测。**
3. **名字从哪来：演员表给候选，照片和对白给线索，人来确认。** 不冷门的影片，网上都有“角色—演员”表，这是公开事实，直接拿来当名字的候选清单（Wikidata 是 CC0、有正式接口；也可以用户粘贴，或读片尾字幕）。有了清单，“从对白里挖名字”就变成“对上清单里的哪一个”，可靠得多，片头角色介绍也有了依据。再进一步，可以拿主演的照片去比对片中的人脸（学术界的常规做法，腾讯的在审申请也是这条路），在本机做、按人脸簇整体比对。它有三个限制，所以只作为“建议”，不直接念出来：论文里即使用最好的模型也只有约 79% 的精确率，华语片上更低，红毯照和片中造型差别大；照片要有合法来源（TMDb、IMDb、豆瓣的条款不允许这样用，可用的是维基共享资源上自由授权的照片，或用户自己提供的图片）；拿真人照片认人，比匿名聚类更明确地属于“人脸识别”，要律师确认。冷门片、新片没有这些资料时，退回“片内聚类 + 对白线索”。四级：L0 只有外观标签；L1 一条线索；L2 两条不同来源的线索一致（例如照片比对 + 对白里的称呼）；L3 人确认过。
4. **点名时机有两派。** Netflix / ACB：“最好”等影片揭示名字。中国大陆有记录的做法：主角一出场就点名，片头用不到 200 字介绍主要角色。你的需求与大陆做法一致 → 点名规则做成参数。
5. **“错名比泛称更糟”是我们的设计假设。** RNIB 与萨里大学 2025 年的测试里，AI 口述的错误包括认错角色，所有视障参与者都说必须有人审；另一项研究里视障者对 AI 场景描述的信任度是 2.43/4。没有找到专门研究“点名”的视障用户研究。设计原则：宁可不说名字，不可说错。
6. **声音分五层，实测优先。** 读屏（含盲文）、系统语音、离线神经语音（Kokoro v1.1-zh，Apache-2.0）、云端神经语音（用户自己的 Key）、真人录音。ACB 准则：真人优先，合成语音须声明并经视障者审核。神经语音和录音要“先合成/录好 → 量真实时长 → 贴进空隙”；读屏没有可靠的“念完了”信号、也无法和影片声音混音，只能估算。
7. **桌面端选 Electron。** 固定版本的 Chromium：两个系统同一套无障碍引擎，现有代码可用。Tauri 在 Mac 上放不了 MKV。但“争渡等中文读屏在 Electron 窗口里好用”**没有任何实机证据**，第一周就要测。
8. **播放。** Electron 能直放 H.264 / 硬解 HEVC / AAC 的 MP4、MKV；AC-3、DTS 音轨和老格式要用 ffmpeg 规范化。必须用 LGPL 版 ffmpeg（`ffmpeg-static` 是 GPL；Windows 有现成的 LGPL 构建，macOS 要自己编）。
9. **法律。** 中国《人脸识别技术应用安全管理办法》（2025-06-01）：人脸信息默认存本机、不得经互联网外传，对工具提供方没有“家庭使用”豁免；对电影里的演员做聚类算不算，条文没回答；法律意义上的“单独同意”指被拍到的人，不是软件用户。版权：《马拉喀什条约》不覆盖电影；中国只允许非营利、已备案机构向经核实的阅读障碍者提供无障碍版本；单独分发口播稿/口述音轨各法域未有定论。AI 标识：中国要求 AI 生成内容带元数据标识，欧盟 AI 法第 50 条上线即适用；自带 Key 的桌面软件算不算“服务提供者”未有答案。
10. **签名。** Apple 开发者账号（99 美元/年）绕不开。Windows：微软商店个人账号免费但只限非商业、且不能转公司账号，能否在大陆注册未核实；SignPath 免费但要求项目已有信誉、排除商业双重授权，新软件可能被拒；Certum 开源证书 49 欧元，另需本人名下账单。商店以外的任何签名在积累信誉前（数周、数百次安装）仍会弹 SmartScreen。仓库里已经规划了收费的 Cloud Plus——**是否成立主体、走哪条路，第一周就要定**。
11. **市场与同类（2026-11-15 开放检索，详见 `docs/film/competitors-and-patents.zh-CN.md`）。** 纯 AI 口述已是每成品分钟 1–2 美元的大路货。单项上都有人做了：AI-Media 的 LEXI AD（云端）能把上传视频里的人脸自动分组、由客户在生成前标名字；腾讯有在审专利申请（人脸库 + 角色名对照 + 名字只说一次，名字取自百科）；浙大的 EagleMovie / EasyAD 是给中国盲文图书馆做的桌面制作工具（不管人物）；腾讯视频、优酷的无障碍剧场是封闭的内部流水线并有视障测评员；还有视障开发者写的 ScriptGrid（MIT）和一个“名字来自字幕”的演示。没有找到一个可安装的开放工具，在用户自己的影片文件上同时做到：人确认的角色库、代码强制的点名闸门、着装记忆、中文读屏、全程本机且许可宽松。平台不公开它们怎么点名，这是没披露，不是做不到。志愿者制作方（光明影院等）一部片子写稿约 60 小时、整片 28 天到 2 个月。法规拉动弱：只有美国 FCC 是硬性要求。专利库没有查全，另有一批要交给律师的线索（字幕间隔与推荐字数、把描述贴进间隔、编辑器、对时）。
12. **成本。** 一部两小时影片的模型费约 0.25–13 美元（国内约 2–20 元）（待测），与扩展“每小时 0.16–0.35 美元”不是一个量级。

## 四、产品：一个软件，两个入口

**听电影**（视障观众）

- **先有声音，再谈设置。** 首次打开，焦点落在“听示例”按钮上（不自动播放，免得和读屏报窗口撞在一起）；示例是开放授权短片配好的口述，示范“点名”。不要求 Key、不下载模型。这些只在用户打开自己的影片时逐项询问。要 Key 的那一步如实说明哪一家、哪几步（验证码、实名、充值）可能需要明眼人陪同过一次。
- **打开影片**：软件念“《X》，2 小时 4 分钟，普通话，有中文字幕，还没有口述。”有匹配的口述包就优先提供（播放口述包不需要任何模型或 Key）。外语片明确告知“本版不念字幕”。
- **两种开始方式**：**先准备再看**（默认；可以“好了通知我”，系统通知加提示音，准备期间阻止电脑睡眠）；**马上开始**（先分析开头十分钟就开播，只用外观标签和已确认的名字）。
- **沉默必须有解释**（每种只说一次，排在口述后面）：后面还没准备好 / 网络断了、已准备到几分钟 / Key 无效或余额用完 / 后台进程正在恢复 / 改用较慢的方式、新的预计时间。菜单里的“状态”随时报当前阶段和剩余时间。
- **名字确认卡**（等待时就能做，最多 8 张，一张对应一个候选人物）：“人物甲：长发女人，开场穿红裙子，出场 34 分钟。3 分 12 秒有个男人喊‘马修，等等’；另一处……。软件根据画面判断被叫的是她，共两条线索，未经明眼人核对。叫她马修吗？”键：是 / 否 / 重听那几句台词 / 自己输入 / 和某某是同一人 / 先别揭示。
  - 给独自使用的视障者的卡，只出给已有两条独立线索的人物，且只限 K11 实测“名字挂对人”≥95% 的证据档；不够的继续用外观标签。
  - 防剧透：只引用“播放位置”与“开头 20 分钟（待测）”两者中较晚者之前的证据；更晚的线索等播放越过后、在下一次暂停时出卡，确认后说一句过渡语再改用名字。
  - 视障者的确认记为“听辨确认”，与“明眼人核对”分开存；口述包里如实写明。
- **默认只念经人确认过的名字。** 自动定名（L2）默认关，K11 与成绩单达标后才作为可选项。未确认的人物始终用同一个外观标签。
- **按键**：播放区是 `role="application"`，约 8 个单键（空格、左右、D 现在描述、R 重复、S 停、W 谁在画面里、X 名字错了、? 帮助），按物理键位匹配；每个动作在原生菜单里另有带修饰键的快捷键，读屏不放行单键时照样可用。确认卡、日志、设置在播放区之外，用真按钮。
- **W** 由本机身份层直接回答，不调模型。**X** 给三个选项（这不是马修 / 她名字不对 / 永远别点她的名）：整片文字立刻改对，不重新生成、不调模型；合成声自动重念受影响的条；真人录音受影响的条改用合成声，并把纠错存成文件可发回志愿者。
- **默认用软件自己的声音念口述，界面仍由读屏念。** 原因：读屏没有“念完了”的信号、按键会打断、无法和影片混音。但读屏自己的播报软件管不住，所以规定：用户做了会让读屏开口的操作（Tab、开菜单/对话框/确认卡、按 X），软件声音立刻停下当前这条口述、不补念（留在日志里，R 可重听）；软件随后要说的话等读屏说完再出。“用我的读屏念口述”一键可切；嫌软件声音慢的用户，默认由读屏念。最终默认按读屏逐个由 K3 实测决定。
- 当前口述始终有一行可聚焦的文字和日志（盲文点显器、低视力大字）；界面跟随系统高对比、放大到 200% 不丢内容、焦点框明显。更新提示绝不在播放中弹出。

**制作台**（志愿者、机构）

1. **角色表**：每个人脸簇的缩略图（只在本机）、出场时长、候选名字和证据；合并 / 拆分 / “同时饰演…” / 标为群众 / 剧透锁 / 读音。
2. **稿件**：逐条显示入点、出点、空隙秒数、字数上限、正文、涉及人物、状态；贴合表文字为先（“合适，余 0.8 秒”“超 0.6 秒，约 3 个字”）；输入 `@` 插入人物；检查项：揭示前点名、他/她歧义、压对白、着装重复。
3. **审校**（免费、本机、不阻塞导出）：草稿 → 已改 → 明眼人校对 → 视障审听 → 定稿。视障审听就是边放影片边听，按键标记问题，沉默即通过。
   - **核对模式（门槛最低的志愿者任务）**：不用写稿，只看影片和口述文字，逐条判“对 / 不对 / 改一下”。软件把要核对的东西排好队：先是名字（每个主角给几个出场片段，问“这是不是冷锋”——几分钟就能把全片的名字从“听辨确认”升级为“明眼核对”），再是校验器标了“待核”的条目，再是最重要的口述。核对到哪算哪：只核完名字就交回来，也已经有用。
   - **一版一版地出**：AI 版马上可用，标明“AI 起草，未经人核对”；志愿者每核对或修改一轮，就是新的一版。每条口述都记着自己的状态（AI / 已核对 / 已修改 / 视障审听过），软件能念出“本片口述第 2 版：名字已经明眼志愿者核对，正文核对了六成”。听众拿到新版后，已核对的名字立刻生效。
4. **录音**：开录前先把本条念一遍（同时是一行可聚焦文字）；三秒原声预卷、提示音倒计时；从倒计时结束到停止采集软件不出任何声；预卷时自检麦克风，录到外放声就先说“请戴耳机”；录完念质检（时长、超出空隙多少、峰值、底噪），可重录或变速 10%。
5. **出与进**：导出口播稿 DOCX / XLSX / CSV / SRT / WebVTT（之后加 DAPT）和逐条 WAV；也能把在 Word / Excel 里改过的稿子、在别处一口气录完的整段录音导回来（按条切分）。律师答复前，导出的稿子只带时间码，不带台词。导入导出与现有工具互通：中国盲文图书馆的稿件样式（待核实）和 ScriptGrid 的 XLSX。
6. **口述包 `.svad`**（带版本号和逐条核对状态；志愿者要用自己手里的那份影片来核对——我们不分发影片，口述包里也没有影片内容）：稿子 + 可再分发的录音 + 只含名字的角色表 + 对时指纹，不含影片的画面、声音、台词。包上写“本包声明：AI 起草 / 人工修改 / 视障者审听 / 真人配音 / 角色名经听辨或明眼核对”。

## 五、技术方案

### 5.1 架构与仓库边界

```
src/film/     新增：电影引擎，纯 ES 模块，零依赖。只允许相对导入 src/film 和 src/shared 白名单内的纯模块；
```

### 5.2 身份层：与人脸解耦

```
IdentityProvider.visibleAt(t) → [{characterId, box, conf, trackId}]
  GroundTruthIdentity   手工标注（实验与自动化测试；先证明“点名”有价值，再赌人脸模型）
  FaceClusterIdentity   本机人脸聚类
  PromptBankIdentity    无人脸模式
```

**预处理各阶段**（产物落盘为带 `{version, inputsHash}` 的文件，可续跑；时间一律落在实际播放的那个文件的 `currentTime` 轴上，偏差 ≤50 毫秒由 K4 实测）：

| 阶段 | 做什么 | 预算（两小时影片，待测） |
| --- | --- | --- |
| 探测 | ffprobe 定播放路径、音轨、字幕轨 | 秒级 |
| 解码一遍 | 每秒 2 帧落盘为 JPEG 帧库（长边约 960，约 1 GB，计入缓存配额，成稿后可清；后续阶段只读帧库）、场景分数 → 镜头、16 kHz 单声道音频 | 3–15 分钟 |
| 对白时间轴 | 内嵌文字字幕轨或用户给的 SRT / ASS / WebVTT（`subs.js`，含 GB18030 解码）；图形字幕或无字幕则本机语音识别 + 语音活动检测 → 空隙（≥1 秒）及各空隙字数上限 | 0–15 分钟 |
| 人脸 | YuNet（整帧 + 分块找小脸）→ 对齐 → 特征 → 镜头内追踪 → 约束聚类（同轨必连、同帧必不连、人的合并拆分成为永久约束；**宁多分、不错并**）→ 按出场时长 × 脸大小取前 12 为可锁定主角 | 8–30 分钟 |
| 名字线索 | 纯文字模型按 10 分钟窗口读对白提取 `{名字, 类型, 时间, 台词}`；对最强的 ≤150 条线索各用 3–4 张编号帧问模型“被叫的/说话的是几号，或无法判断”；累计投票；两条线索相隔 ≥90 秒（待测）或类型不同才算独立 | 2–4 分钟，几毛钱 |

- **演员表与参照照片（有就用）**：演员表（角色名—演员名）把名字限定在几个候选里；每位主演若有参照照片，就把照片的人脸特征和各人脸簇的平均特征比对，给出“人物甲像是某某饰演的某某”的建议和把握度。比对按簇做而不是逐帧做，所以不增加多少计算；找出主角在哪些画面出现仍然要把影片扫一遍，这一步省不掉，但它在本机跑、不花钱。群演的簇排在出场时长的末尾，不进角色表、不出确认卡、不产生任何费用。
- 特征模型默认 SFace；AuraFace 只取 `glintr100.onnx`，拿到书面来源说明或律师签字前不作默认。人脸后端候选：原生 onnxruntime-node，或渲染进程 Worker 里的 onnxruntime-web（少一个原生依赖；其模型推理耗时同样未测），K4 定夺。
- 语音识别默认 SenseVoice-Small：其模型许可条文写“仅供参考学习”，商用依据只是维护者的说明，所以从官方权重自行导出、并列入律师清单；不认可就换 Whisper（MIT）。
- **无人脸模式**（动画、暗片、用户不开启、或律师说不行时的正式形态）：按 id 的文字角色库随段携带，不画框、不产生人脸数据；名字只来自人输入或确认；“可见轨迹”检查不适用且不视为通过，能否填名字由 K1 的“无编号框”一臂决定，没过就只填前后一致的外观标签；W 回答“最近一条口述提到的人物”并说明本模式不核对画面。

### 5.3 占位符与点名闸门（核心设计）

**模型永远不写名字，只写占位符 `{P3}`；名字由纯函数在播放和导出时填入。**

```
Character  {id:'P3', name|null, level:0..3, aliases:[…], say(读音), descriptor:{zh,en},   // 外观标签只写不随换装变的特征
            revealAt|null, spoilerLock, main, screenSec,
            evidence:[{t, kind:'vocative'|'self-intro'|'on-screen'|'credits'|'human', by?:'ear'|'sight', quote}],
            clusters:[…] }                                       // clusters 仅本机
Appearance {char, scene, from, to, outfit, src:'model'|'human'}  // 着装一律取自这里
Slot       {id, start, end, room, budget:{brief,standard,detailed}, src:'subs'|'vad'|'asr'}
FilmCue    {id, slot, start, end, kind, priority, brief, standard, detailed,              // 正文带 {P3}
            people:[{char, tracks}], scene, status, by:'ai'|'human', clip?:{file, dur, voice, textHash}}

renderScript(filmScript, cast, policy, {lang, rateProfile}) → {cues, report}   // 纯函数，零模型调用
verifyCue(cue, trackIndex, cast) → cue | 降级 | 不念并标记
toPlayerScript(…) → 现有 v2 口述格式（gapMeasured:true，每条另带 id）
```

闸门规则：

- 级别不够（默认要 L3）、未到 `revealAt`、或有剧透锁 → 填外观标签：“长发女人走到窗边”。
- “首次出场即点名”（中文默认）→ 第一次“名字 + 外观 + 着装”，之后只用名字；“随剧情揭示” → 揭示时说一次“外观，名字”，之后只用名字。
- 着装只在该场景第一次、换装、或久未出现后重新挂钩时说（“马修，换了灰大衣，……”）。
- 填完按空隙再核一次时长，超了依次退到 详细 → 标准 → 简短 → 仅标签。出口断言：朗读和导出文本不得残留花括号或编号，命中则该条不念。

校验器：

- 占位符指向的人在判定范围内没有可见轨迹 → 降级为外观标签。判定范围是参数（起始值 [起点 −3 秒, 终点 +1 秒]）；它既可能放过“两人都在场却指错”，也可能在侧脸、背身、暗场时误降。用哪条规则由 K1 / K1b 量出的漏放率和误降率决定。
- 正文里出现角色表中的名字（≥2 字的专名；画面文字引文除外）→ 视为格式违规，不盲目改回占位符；交给一次补救调用，补救后仍有名字 → 该条不念，制作台标“待核”。
- 全角花括号本地规范化；`{P99}`、裸写的“3 号”“红框”同样按违规处理。
- 锁定角色在场却写了“一个女人”：只在该时间窗内仅有这一条人物轨迹时改成占位符，否则保留并计入“泛称复发率”。

人改动之后要重跑什么：

| 人的操作 | 重跑 | 模型调用 |
| --- | --- | --- |
| 改名、别名、确认、设揭示点、剧透锁、换点名规则 | 只重填 | 0 |
| 合并两个簇 | 占位符改写 + 校验 + 重填 | 0 |
| 拆分一个簇 | 按轨迹改写；有歧义的块重做 | 仅受影响的块 |
| 换字幕文件 | 时间轴、名字线索、成稿 | 仅文字 |

重填后文字变了的音频片段即作废：本机合成声后台自动重合成；云端语音在已同意的用量内重合成，失败则该条退回本机语音；真人录音标“需重录”，暂用合成声。

### 5.4 口述生成

- 10 分钟分段，段界对齐镜头切换。选帧起点规则（K1 定稿）：每个镜头 1 帧，超过 6 秒的镜头每 3 秒加 1 帧；每块 ≤60 帧（各模型上限来自登记表）。帧上画彩色编号框（脸太小时框人），文字对照表写“P3（红）：长发女人；当前着装 红裙子；已确认名 马修”，名字不画进图。画框是 `marks.js` 里在像素缓冲上画矩形和点阵数字的纯函数，命令行实验与应用共用，K1 测的就是上线的画法。
- 输入另含：本段对白及时间、空隙清单与字数上限、前 10 分钟的稿子、滚动剧情摘要。输出：口述条目（带占位符、三档长度、`people`）、`sceneStarts`（吸附到镜头切点）、`appearances`（只在未登记或着装确实不同时返回）。本地按 schema 校验，模型不支持严格 JSON 时降级为“json_object / 提示词 + 本地修复 + 一次补救调用”。
- 单阶段还是两阶段（先逐镜头事实，再按字数上限成稿）由 K1 决定。云端调用计划（待测）：约 30–60 个请求，每个 4–6 MB，每家并发 2，全程 10–25 分钟。

### 5.5 声音

`SpeechBus` 是软件里唯一能出声的地方，保证软件自己不会同时出两个声音；状态和进度排在口述后面，绝不打断口述。读屏自己的播报按第四节的规则让路。

| 层 | 实现 | 时长 | 1.0 |
| --- | --- | --- | --- |
| 读屏 / 盲文 | live region；需要时经 Prism 直连 | 估算 | 是 |
| 系统语音 | Chromium Web Speech | 估算 | 是 |
| 离线神经语音 | sherpa-onnx + Kokoro v1.1-zh / v1.0，前置数字与生僻词规范化 | 实测 | 是 |
| 云端神经语音 | 阿里 qwen3-tts-flash（HTTPS 流式，含方言） | 实测 | 是（仅本机收听；其合成音频在核实百炼协议前不进口述包） |
| 真人录音 | 制作台录制或口述包自带 | 实测 | 是 |
| 其他云端语音 | Azure、ElevenLabs、MiniMax、Gemini TTS 等 | 实测 | 逐家核实再分发条款并用真 Key 跑通后再加 |

- 估算层（读屏、系统语音）直接用现有 `Playback`。实测层和录音不走 `chooseUtterance`：`desktop/renderer/filmplayback.js` 里 `FilmPlayback extends Playback`，只覆写选句与播放，按口述 id 向 `src/film/voice/fit.js` 取“用哪个版本、变速多少、要不要暂停”和对应音频；`desktop/test` 钉住基类被覆写的方法，网页播放器改了签名就失败。
- 贴合顺序：能放进空隙的最长版本 → 保音高变速（signalsmith-stretch，上限 1.2 倍，K6 验证）→ 换短版本 →（暂停模式）暂停影片。“清晰慢速”预设不变速，顺序改为 换短句 → 暂停。“零压对白”只对实测层承诺。
- 合成是可续跑的后台阶段，按（声音，文字哈希）缓存，从播放位置往前滚动预合成；到点还没好的用系统语音按估算念。
- 压低影片声音用 `video.volume` 渐变（沿用 `src/content/index.js:1304-1318`），自家音频走 Web Audio。读屏语速用“请在读屏念完时按回车”的三句校准。预设：清晰慢速 / 快速 / 讲述。

### 5.6 播放与媒体

`<video>` + 自定义协议（多 GB 文件的区间请求由 K4 验证，不行就退到本机回环服务）。内测阶段只接受能直放的文件；随后加规范化入口：直放 → 一次性规范化到缓存（视频流拷贝、所选音轨转 AAC）→ 老格式转码。优先用系统硬件编解码器；不自带 x264 / x265；软件 H.264 编码只用安装后从 Cisco 下载的 OpenH264。缓存、帧库、模型有磁盘配额和清理界面。

### 5.7 多模型接口

- `src/film/models/catalog.js`：能力登记表（收不收图、单次最多图数、JSON 级别、输出上限字段名、长上下文加价门槛、带生效日期的价格、可用地区、**K1 实测成绩**）。`routing.js`：按任务路由（初筛 / 成稿 / 挖名字）；**带人物的成稿只路由到 K1 过关的模型**，没测过的（含用户自填的任意接口）只用外观标签并说明原因。
- `wire.js`：按登记表自建请求体，每次尝试自带超时和重试。复用的是客户端本身——`QwenClient.chat(body)`（带 `apiBase` 的 OpenAI 兼容客户端）和 `GeminiClient.generate(body, …)`——不复用扩展的适配层（`describe.js` 的 `ADAPTERS` 未导出，`describeFrames` 写死了扩展的提示词和会丢字段的 `normalizeChunk`）。
- 按协议应可覆盖千问、豆包、智谱、Kimi、DeepSeek、OpenRouter、硅基流动、本机 Ollama（待测）；每家用真 Key 跑通后才列入预设。两套预设都从 M2 起提供，默认按所在地区选：Gemini、Claude 不对中国大陆和香港提供服务（OpenAI 同样不对大陆开放），所以大陆用户默认用国内模型（千问 / 豆包 / DeepSeek）；其他地区、或自己有海外 Key 的用户，默认用 K1 成绩最好的模型（Gemini 原生；GPT、Claude 经 OpenRouter）。哪个模型“更先进”不靠印象定，由 K1 在同一批华语片分段上的成绩定。
- 全离线描述（本机小视觉模型）一部片要几个小时，只作“实验性”，连用户自己的 Ollama。

### 5.8 口述包与对时

`.svad`（zip）：`manifest.json`（版本、片名/年份/时长/参考音轨语言、制作与审校声明、AI 标识、许可证、各文件 SHA-256）、稿子、只含名字的角色表、`audio/*.opus`、`sync.bin`（不可逆指纹）。首版只做完整性校验。包里不出现文件名、路径、文件哈希、台词。只收登记为“可再分发”的音频（真人录音、Kokoro），由导出器的字段白名单强制。

对时自己写（Olaf、Panako、alass 是 GPL/AGPL；ffsubsync、Sushi 对的不是空隙或需要两条音轨）：帧率比 → 全局偏移 → 分段 → 逐条把握度 → 按键微调；对完再按本机语音活动核一遍。K7 不过，口述包只在同一机构内部流转。

### 5.9 合规规则（写进代码和测试）

1. 人脸数据存 `userData/faces/<filmId>/`，在工程目录之外；按影片隔离、一键删除、不跨片比对、不比对任何身份库；导出器和请求构造器都是字段白名单。首次聚类前向用户单独说明并由用户开启——这是知情开关，不是法律意义上演员本人的“单独同意”，合法性依据由 K10 给出。
2. 人脸比对只能提出建议：名字要经人确认，或与影片自己的对白线索一致，才会念出来。从不问云端模型“这是谁”；参照照片和人脸特征都不出本机。演员表只取文字（角色名、演员名），来源限于有授权的（Wikidata、用户粘贴、片尾字幕）；参照照片限于自由授权或用户自备，不抓取 TMDb、IMDb、豆瓣。“画了编号框的画面 + 台词”会发给云端模型，写进知情说明并列入 K10；律师不允许时改发“不画框的帧 + 文字角色库”（K1 已量过这条退路的损失）。
3. 不读任何 DRM 内容；软件用途写明是影视作品，不用于家庭录像或监控；软件与文档不指引任何获取或翻录影片的途径。
4. 口述包不含画面、声音、台词；发布时勾选“影片来源合法”；公开的登记/索引在律师意见前不开。
5. AI 标识元数据始终写入；可听提示每部至少播一次、界面标识常显；能否关闭待 K10d。
6. `desktop/models/manifest.json` 是白名单：每个权重登记许可证、来源、SHA-256，模型管理器只下载登记项；CI 另设黑名单（ffmpeg-static、InsightFace/SCRFD、Piper、Rubber Band、Olaf/Panako、alass）。声音克隆不做。

### 5.10 评测

- 头号指标：**每 100 条口述的错名数**、**每听 30 分钟的错名数**，同时报**点名覆盖率**（否则“从不点名”也能过关）。其余：名字挂对人的精确率与弃权率、过早点名数、泛称复发率、着装错漏、簇纯度与错并率、压对白占比、各阶段耗时、志愿者改稿量与人工小时数、视障评审评分。按确认来源（听辨 / 明眼）分别报。
- 每个实验产出 `KillTestReport {id, metric, value, threshold, pass, film, source, model, date}`，提交到 `docs/film/killtests/`——这就是给投资人看的数据室。
- **测试影片的来源规则**：每部登记来源类别和凭证（凭证留在仓库外）：开放授权；公有领域（中国：发表满 50 年，待律师确认）；你自己购买的无 DRM 文件或未加密光盘；版权方或伙伴机构授权提供。没有凭证的不进测试集。近年华语片只在伙伴或版权方提供时才测，此前报告里如实写“不含近年华语片”。
- 可借用的公开评测资源：StreamCast 的 MCN 数据集与指标（Apache-2.0）；Movie101 / Movie101v2（CC-BY-4.0，203 部华语片的口述文本与角色名标注，不含影片）。
- 自动化夹具用开放授权影片（如 Tears of Steel，许可证落地时核实）。发布流程没有新成绩单或成绩倒退就失败。一条命令跑通“夹具影片 + 本机假模型 + 假语音服务”的全流程，供 AI 代理自测。

**M3 稳健输入与发布工程（第 14–17 周）**：播放规范化与转码、自建并签名的 macOS LGPL ffmpeg、无字幕时本机语音识别、马上开始、模型管理器（SHA-256、断点续传、魔搭 → 自有香港存储 → hf-mirror → GitHub）、内置示例、签名安装包、更新、桌面隐私文档。只出 Windows x64 和 macOS arm64；Windows 渠道默认是签名的 NSIS 安装包放 GitHub Releases 与镜像。安装包体积第 1 周就量（Electron 本体已 80–100 MB；后取的可执行文件必须带我们的签名）。
退出：20 个文件的样本库 ≥90% 能播；K4 在 Windows 上成立。关口 **G3（任何公开构建之前全过）**：K8；K10 四问各自过关或已切到退路；若律师认定适用，影响评估已完成；AI 元数据标识；成绩单（错名率与覆盖率均过 M2 门槛）；演练“先发桌面版、再发扩展 `v*` 版，旧桌面版仍能更新”；安装包自检（各进程加载原生模块并跑一次推理）。

**M4 声音库（第 18–20 周）**：Kokoro、实测贴合与变速、`FilmPlayback`、三套预设、试听。退出：实测层 ≥95% 的片段在空隙内结束、压对白为零；K6 成立；5 位视障用户（两位 60 岁以上）能独立选好声音。

**M5 制作台完整版（第 21–25 周）**：审校状态与视障审听、逐条录音与质检播报、稿子和整段录音导回、XLSX / SRT / WebVTT / DAPT 导出；核对模式、版本号与逐条核对状态；口述包 v0（志愿者和听众用同一份拷贝时直接可用，不需要对时）。退出：新志愿者 2 小时内完成一段 10 分钟的审定稿（按 60 小时/部折算约 5 小时）；视障评审靠听完成审校；一位用读屏的视障测试者只靠听或点显器独立录完 10 条，成品里没有读屏声和串音。→ **1.0**

**M6 跨拷贝对时与分享（第 26–29 周，仅当 K7 过）**：口述包在不同拷贝之间对时、听众纠错文件、（律师意见之后）公开的口述包登记与“求片单”。退出：A 拷贝做的包在 B 拷贝上 95% 的口述误差 ≤300 毫秒，否则明确走手动。

约 29 周是乐观估计；真正决定进度的是测试者、账号和律师。

**之后**：自动 L2 定名、更多云端语音、外语片念字幕（1.0 之后第一件事）、供本人手机收听的“带口述音轨”导出（需律师意见）、动画路径、机构版、把占位符与闸门回灌进浏览器扩展。

**明确不做**：读 DRM、云端人脸服务、演员剧照比对、分享人脸特征或缩略图、声音克隆、早期的免 Key 中转服务（那会让运营者成为处理电影画面的生成式 AI 服务提供者）。

## 十一、商业与融资叙事（简）

- **卖流程，不卖分钟。** 软件本身对自带 Key 的个人永久免费：播放、角色锁定、制作台、录音、所有导出、所有无障碍设置。模型费由用户自己的 Key 承担；不用 Key 能听的只有内置示例和口述包。
- **钱从哪来**：前期费用由你自付；公益与科研基金均未申请、未核实，不作为前提。之后找 3–5 家机构试点（志愿者团体、盲校、图书馆、公益影院），卖上手培训、支持和托管的团队空间（不在本计划 29 周内；需主体，境内托管需 ICP，并经律师意见）；对外发行通过已在版权局备案的非营利伙伴。价格与规模都是待验证的假设。
- **差异化（按 2026-11-15 的开放检索）**：不再说“人脸分组加人工标名”“从对白取名”“占位符”“志愿者制作台”是新的——它们各自都有人做了。站得住的是这一组合：人确认的角色库 + 由代码强制的点名闸门 + 着装记忆 + 视障者靠听就能确认 + 中文读屏 + 在用户自己的影片文件上全程本机、许可宽松、开源，再加公开的评测数据。最接近的是 LEXI AD（云端、客户标名）和腾讯的在审申请（名字取自百科、无人确认）。不比速度（优酷、腾讯已把制作周期缩到几天），比名字不出错。专利库没有查全，对外不说“没有同类专利”。
- **不算护城河的**：角色名字是公开事实；本机软件不收集数据；MIT 的包格式是推广手段。真正的积累是评测集与成绩单、视障评审小组、合作伙伴的发行授权、志愿者网络。
- **坦率的判断**：单做口述影像是小众市场，没有可靠的市场规模数字；上市级的故事要从这个楔子扩展到更宽的无障碍与本地化内容平台，并且需要一个持有知识产权和商标的主体。
